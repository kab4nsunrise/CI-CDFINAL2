# Описание проекта: Настройка GitHub Actions workflow для CI/CD

Данный проект является завершающим этапом работы над приложением, которое вы уже контейнеризировали с помощью Docker. Теперь вам предстоит настроить автоматический конвейер (CI/CD) на основе GitHub Actions. Ваш workflow будет выполнять две ключевые задачи: **автоматическое тестирование** кода при каждом изменении и **автоматическую публикацию** Docker-образа в DockerHub при добавлении тегов. Это задание закрепляет навыки работы с современными инструментами непрерывной интеграции и доставки.



## Актуальность и контекст

CI/CD (Continuous Integration / Continuous Delivery) — неотъемлемая часть современной разработки. Настроив автоматические проверки и публикацию, вы избавляете себя от рутинных операций, снижаете риск человеческой ошибки и ускоряете доставку новых версий продукта. GitHub Actions предоставляет гибкий и мощный инструмент для построения таких конвейеров прямо в вашем репозитории. В рамках этого задания вы примените полученные знания на практике, создав workflow, который будет:
- проверять корректность кода с помощью линтеров и запускать модульные тесты;
- собирать Docker-образ и публиковать его в реестр DockerHub, но только для помеченных релизов (тегов).



## Цель работы

1. Создать файл workflow в директории `.github/workflows/` с именем, например, `ci-cd.yml`.
2. Настроить два отдельных **job**:
   - **test**: запускает проверку кода (например, `go test`, `pytest`, `npm test` и т.п.) и, при необходимости, линтеры (например, `golangci-lint`, `eslint`).
   - **publish**: выполняется только при условии, что на коммит установлен Git-тег (например, `v1.0.0`). Собирает Docker-образ, логинится в DockerHub (используя секреты), присваивает тег (например, `latest` и версию) и публикует его.
3. Использовать учётную запись GitHub (при этом секреты для DockerHub должны быть добавлены в настройках репозитория).
4. Убедиться, что после успешного выполнения workflow образ доступен для скачивания и запуска из DockerHub.

-

## Требования к workflow

### Job 1: `test`
- Запускается на каждом push или pull request (обычно триггер: `push` и `pull_request`).
- Использует среду выполнения (например, `ubuntu-latest`).
- Устанавливает необходимые инструменты (язык программирования, зависимости).
- Выполняет команды для запуска тестов и статического анализа (например, `go test ./...`, `golangci-lint run`).
- Если тесты или линтер падают, workflow должен завершиться с ошибкой.

### Job 2: `publish`
- Запускается **только** при создании тега (или при пуше тега) — обычно используют условие `if: startsWith(github.ref, 'refs/tags/')`.
- Использует ту же среду выполнения.
- Логинится в DockerHub с помощью логина и пароля/токена, которые хранятся в **секретах** (`DOCKER_USERNAME` и `DOCKER_PASSWORD` или `DOCKER_TOKEN`).
- Собирает образ командой `docker build`.
- Присваивает образу два тега:
  - `<ваш_docker_id>/<имя_образа>:latest`
  - `<ваш_docker_id>/<имя_образа>:<название_тега_релиза>` (например, `v1.0.0`).
- Публикует образ в DockerHub (команда `docker push`).



## Структура проекта

После настройки workflow структура репозитория будет выглядеть так:

```

├── .github/
```

## Инструкция по выполнению

1. **Подготовка репозитория**  
   Убедитесь, что у вас есть репозиторий, созданный из шаблона, с уже готовым приложением и Dockerfile.

2. **Добавление секретов в GitHub**  
   Перейдите в настройки репозитория (`Settings` → `Secrets and variables` → `Actions`) и добавьте два секрета:
   - `DOCKER_USERNAME` — ваше имя пользователя DockerHub.
   - `DOCKER_PASSWORD` — пароль или токен доступа (токен предпочтительнее, его можно создать в настройках DockerHub).

3. **Создание файла workflow**  
   В корневой директории создайте папку `.github/workflows/`, внутри неё файл `ci-cd.yml` (или любое другое имя с расширением `.yml`).

4. **Написание workflow**  
   Опишите два job: `test` и `publish`. Для `test` укажите шаги: checkout кода, установка языка и зависимостей, запуск тестов. Для `publish` добавьте условие на теги, шаги для логина в DockerHub, сборки и пуша.

5. **Тестирование**  
   Сделайте коммит и пуш в ветку (например, `main`), чтобы проверить, что job `test` запускается и проходит. Затем создайте тег и отправьте его в репозиторий:
   ```bash
   git tag v1.0.0
   git push origin v1.0.0
   ```
   После этого должен запуститься job `publish`. Проверьте в интерфейсе Actions, что оба job завершились успешно.

6. **Проверка публикации**  
   Зайдите на свой профиль DockerHub и убедитесь, что образ с тегом `latest` и тегом `v1.0.0` появился. Попробуйте запустить контейнер из этого образа на локальной машине:
   ```bash
   docker pull <ваш_docker_id>/<имя_образа>:v1.0.0
   docker run -p 8080:8080 <ваш_docker_id>/<имя_образа>:v1.0.0
   ```
   Убедитесь, что приложение запускается и работает.

7. **Создание Pull Request**  
   Если вы работали в отдельной ветке, создайте PR в основную ветку. После того как все проверки пройдут, отправьте ссылку на PR на проверку.



## Критерии проверки

- Файл workflow существует и корректно оформлен (синтаксис YAML валиден).
- Job `test` выполняется при каждом push и PR, запускает тесты и линтеры (если они есть).
- Job `publish` срабатывает только при создании тега и успешно логинится в DockerHub.
- В DockerHub опубликован образ с тегами `latest` и <версия_тега>.
- Образ скачивается и запускается без ошибок.
- В репозитории не хранятся пароли или токены в открытом виде (используются секреты).



## Рекомендации

- Используйте официальные Actions, чтобы упростить настройку, например:
  - `actions/checkout@v3` — для клонирования кода.
  - `docker/login-action@v2` — для логина в DockerHub (с передачей секретов).
  - `docker/build-push-action@v4` — для сборки и пуша образа (можно объединить в один шаг).
- Для тестов можете использовать `actions/setup-go@v4` или аналоги для других языков.
- В условии `if` для job `publish` используйте `github.ref` для проверки, что это тег:
  ```yaml
  if: startsWith(github.ref, 'refs/tags/')
  ```
- Для получения имени тега используйте `github.ref_name` (включает только имя тега без префикса `refs/tags/`).
